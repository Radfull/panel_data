# Тестовое задание

Задача - разработать веб-сервис для оценки модели на панельных данных с фиксированными эффектами

Эндпоинт для построения модели должен возвращать:
- сериализованную модель (выберите любой подходящий способ), которую можно потом использовать для инференса и анализа ее остатков.
- прогноз на обучающей выборке
- метрики
- данные по оценке коэффициентов (можно опираться на вывод, который обычно есть в основных статистических пакетах)

### Важно продумать:
- Какие есть сущности, какие типы у ее элементов, какие у них ограничения на параметры
- Как декомпозировать задачу для простой расширяемости и поддерживаемости кода

### Что приветствуется:
- Глубокая проработанность доменной логики (полезный возвращаемый результат, а не просто какие то доступные поля; проработка стратегий при различных исключениях; и др.) 
- Интересные инструменты для DDD, помогающие решить сложные задачи (например stories, results, различные паттерны)

### Что не приветствуется:
- Слабое понимание домена задачи, упор на инфраструктуру 
- Нарушение принципов чистой архитектуры
- Отсутствие принципов DDD
- Нейрослоп 


### Стек 

Язык - строго python, стек можешь выбрать любой удобный, но лучше наш

Стек: Python, uv, Pydantic, FastAPI, statsmodels, linearmodels , NeuralForecast, PyTorch, Dishka, pytest

## Рекомендации по архитектуре 

Слой предствления:
- FastAPI роутер
- эндоинт с DI через dishka, схемами запроса/ответа в pydantic, обработкой ошибок с выбросом 422/400/500 в нужных случаях

Доменный слой:
- доменные сущности и контракты, заранее определенные ошибки (например, ошибка недостатка числа наблюдений)
- конкретная реализация не должна протекать внутрь этих сущностей
- не должна зависеть ни от каких библиотек, кроме встроенных в python

Инфраструктурный слой:
- приветствуется использования паттерна adapter, fabric, strategy и visitor в нужных местах
- зависит только от доменного слоя и минимизирует зависимости от других адаптеров в инфраструктуре 
- инкапсулирует работу с библиотеками (statsmodels, например)

Слой бизнес логики:
- агрегирует различные доменные сущности в бизнес сущности (схемы запроса/ответа)
- не должна зависеть явно ни от каких библиотек, кроме pydantic и встроенных в python
- формирует сценарии использования адаптеров из инфраструктуры, использует только схемы запроса/ответа, определенные в этом слое

## Рекомендации по реализации

### Слой представления:

```python

class UseCaseRequest:
	data: DataEntity
	params: ParamsEntity
	...
	

class UseCaseResponse:
	result: ResultEntity
	...

@router.post('/use_case')
def calculate(
	request: UseCaseRequest,
	uc: DI[UseCaseInteractor]
	) -> UseCaseResponse:
	
	try:
		response = uc.execute(request)
	except UseCaseDomainError1:
		raise HTTPException(...)
	...

```

### Слой приложения:
Реализация доменной логики, сценария использования

```python

class UseCaseInteractor(UseCaseInteractorI):
	def __init__(self, adapter: UseCaseAdapterI, ...):
		# Желательно прокидываются через DI 
		self._adapter = adapter
		...
		
	def calculate(request: UseCaseRequest) -> UseCaseResponse:
		# Бизнес логика сценария
		result = self._adapter.calculate(request.data, request.params)
		
```
